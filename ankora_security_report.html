SEC-HIGH-01: Kimlik Bilgisi Depolama — Base64 Encoding Tek Katman

Yüksek

API anahtarları (OpenAI, Gemini, Groq) credentials.dat dosyasında Base64 ile encode edilerek saklanıyor. Base64 bir şifreleme algoritması değil, encoding standardıdır ve kolayca decode edilebilir. Dosya izinleri 0600 olarak ayarlanmış (yalnızca Unix), ancak disk erişimi olan bir saldırgan tüm API anahtarlarını düz metin olarak okuyabilir.

  • load_credentials() → Base64 decode → JSON parse → ham API anahtarları
  • Saldırı Senaryosu: cat ~/.config/ankora/credentials.dat | base64 -d → tüm anahtarlar ifşa
  • Windows ortamında dosya izin koruması (0600) uygulanamıyor
Öneri

OS-native keychain/keyring entegrasyonu kullanılmalı (Linux: libsecret/GNOME Keyring, macOS: Keychain, Windows: DPAPI). Alternatif olarak AES-256-GCM veya ChaCha20-Poly1305 ile şifreleme uygulanabilir. En azından bir master anahtar türetimi (PBKDF2 veya Argon2) ile korunmalı.

📍 src-tauri/src/main.rs · Satır 271–296 · load_credentials() / save_credentials()

SEC-HIGH-02: Kurulumda Varsayılan Parola Hardcode

Yüksek

Kurulum sihirbazının frontend tarafında, kullanıcı parola girmezse varsayılan olarak "ankora" değeri gönderiliyor. Bu, kurulum sırasında kullanıcının dikkat etmemesi halinde son derece zayıf, tahmin edilebilir bir parola ile sistem kurulmasına yol açar.

  • password: document.getElementById('inst-password')?.value || 'ankora'
  • Bu tür bir fallback değeri brute-force veya wordlist saldırıları için ilk hedef olur
  • Rust backend tarafında parola karmaşıklık doğrulaması bulunmuyor
Öneri

Varsayılan parola fallback'i kaldırılmalı. Kullanıcı boş parola ile kurulum başlatmaya çalışırsa frontend ve backend tarafında hata gösterilmeli. En az 8 karakter, karışık karakter kümesi (harf+rakam+özel) zorunluluğu getirilmeli.

📍 src/app.js · Satır 1356 · InstallerWizard.runInstall()

SEC-MED-01: Gemini API Anahtarı URL Parametresinde Açık İletim

Orta

Google Gemini API çağrılarında API anahtarı ?key=... şeklinde URL query parametresine ekleniyor. Bu, anahtarın HTTP sunucu loglarına, proxy loglarına, tarayıcı geçmişine ve ağ izleme araçlarına sızma riskini artırır.

  • format!("...?key={}", resolved_key) → anahtarın URL'de düz metin olarak görünmesi
  • OpenAI ve Groq için Authorization: Bearer header'ı doğru şekilde kullanılmış
Öneri

Google'ın yeni Gemini API v1 formatı HTTP header tabanlı kimlik doğrulama da destekler. x-goog-api-key header'ı kullanılması tercih edilmeli. Bu, Google'ın kendi önerisidir.

📍 src-tauri/src/main.rs · Satır 864–866 · query_local_ai() → Gemini bloğu

SEC-MED-02: UpdaterManager.formatMarkdown() — Kısıtlı XSS Riski

Orta

Güncelleme notları (release_notes) GitHub API'den alınıp formatMarkdown() fonksiyonuyla HTML'e dönüştürülüyor. Fonksiyon önce escapeHtml() ile temizleme yapıyor, ardından regex ile <h2>, <strong>, <li> etiketleri oluşturuyor. GitHub API yanıtı değiştirilirse (MITM veya repo devralma) sınırlı HTML enjeksiyonu yapılabilir.

  • escapeHtml() uygulandığı için doğrudan <script> enjeksiyonu engelleniyor
  • Ancak bold/heading regex dönüşümleri CSS-based saldırı vektörü açabilir
  • CSP script-src 'self' sayesinde script yürütülmesi engelleniyor — risk sınırlı
Öneri

Güncelleme notlarını sadece textContent ile render edin veya DOMPurify benzeri bir sanitizer kütüphanesi kullanın. Markdown ayrıştırma regex yerine kontrollü bir parser ile yapılmalı.

📍 src/app.js · Satır 2215–2224 · UpdaterManager.formatMarkdown()

SEC-MED-03: Güncelleme İndirme — HTTPS Redirect Takibi Kapalı Ama TLS Doğrulaması Eksik

Orta

Güncelleme indirme istemcisi (download_and_apply_de_update) redirect takibini kapatmış, ancak indirilen .deb paketinin bütünlük doğrulaması (checksum/GPG signature) yapılmıyor. Paket doğrudan dpkg -i ile sisteme kurulabiliyor.

  • Sadece URL prefix kontrolü mevcut (https://github.com/ veya https://objects.githubusercontent.com/)
  • SHA256 checksum doğrulaması yok
  • GPG imza doğrulaması yok
  • İndirilen dosyanın gerçekten valid bir .deb olup olmadığı kontrol edilmiyor
Öneri

GitHub Release'e SHA256 checksum dosyası ekleyin. İndirme sonrası sha256sum veya Rust'ta sha2 crate ile hash doğrulaması yapın. İdeal olarak GPG ile imzalı paketler kullanın.

📍 src-tauri/src/main.rs · Satır 1596–1701 · download_and_apply_de_update()

SEC-MED-04: CSP Politikasında unsafe-inline Style Directive

Orta

Tauri güvenlik yapılandırmasındaki CSP (Content Security Policy) kuralında style-src 'self' 'unsafe-inline' directifi mevcut. Bu, CSS enjeksiyonu saldırılarına (data exfiltration via CSS) kapı aralıyor.

  • script-src 'self' doğru şekilde kısıtlanmış — XSS korunması sağlam
  • object-src 'self' data: → data URI ile obje yükleme potansiyel vektör
  • frame-src 'self' data: blob: → PDF görüntüleme için gerekli, ancak geniş
  • connect-src sadece localhost'a izin veriyor — SSRF önlemi var
Öneri

Tüm inline style'ları CSS dosyasına taşıyıp 'unsafe-inline' kaldırılmalı. object-src daha da kısıtlanabilir. frame-src yalnızca 'self' blob: olabilir (data: kaldırılarak).

📍 src-tauri/tauri.conf.json · Satır 49 · security.csp

SEC-MED-05: rm -rf /tmp/* Whitelist İçinde ve Doğrudan Yürütülebilir

Orta

EXACT_ALLOWED_COMMANDS ve ALLOWED_AGENT_ACTIONS listelerinde rm -rf /tmp/* komutu bulunuyor. Bu, AI ajanı veya terminal üzerinden kullanıcının /tmp dizinini tamamen silmesine olanak tanıyor. Çalışan uygulamaların geçici dosyaları dahil olmak üzere tüm /tmp içeriği silinebilir.

  • Çalışmakta olan uygulamaların soket ve temp dosyalarını bozabilir
  • echo 3 > /proc/sys/vm/drop_caches de listede — sistemin performansını anlık olarak düşürebilir
  • AI ajanı kullanıcı onayı ile bu komutu tetikleyebilir
Öneri

/tmp temizliği için daha güvenli bir yaklaşım benimsenebilir: sadece 24 saatten eski dosyaları temizleyen find /tmp -mtime +1 -delete komutu veya tmpwatch aracı tercih edilmeli.

📍 src-tauri/src/main.rs · Satır 40, 69 · EXACT_ALLOWED_COMMANDS / ALLOWED_AGENT_ACTIONS

✓ Güçlü Yönler — Pozitif Güvenlik Bulguları

Projede doğru uygulanmış, endüstri standartlarına uygun güvenlik mekanizmaları

Katmanlı Komut Yürütme Güvenliği (Whitelist + Kara Liste + Metakarakter Filtresi)

Güçlü

Terminal motoru üçlü koruma katmanı uyguluyor:

  • Kesin Whitelist: EXACT_ALLOWED_COMMANDS — sadece tanımlı komutlar yürütülebilir
  • Kara Liste: FORBIDDEN_LAUNCH_BINARIES — sudo, bash, dd, passwd gibi tehlikeli araçlar kesinlikle engelli
  • Metakarakter Filtresi: ; & | \` $ > < ( ) karakterleri engelleniyor
  • Dizin Geçişi Koruması: .. içeren argümanlar reddediliyor
  • Hassas Dosya Kalıpları: /etc/shadow, SSH anahtarları vb. mutlak engel

Dosya Okuma Güvenliği — 7 Katmanlı Koruma

Güçlü

read_document_file() fonksiyonu yedi ayrı güvenlik kontrolü uyguluyor:

  • Dizin geçişi (..) engeli
  • İzin verilen dosya uzantısı kontrolü (yalnızca pdf, md, txt, conf, log, json, yaml vb.)
  • Kanonik yol çözümleme (canonicalize → symlink bypass önleme)
  • Hassas dosya kalıp eşleşmesi (kanonik yol üzerinde)
  • İzin verilen dizin sınırları (Documents, Downloads, home)
  • Hard-link istismarı tespiti (nlink > 1 reddi)
  • 50 MB dosya boyutu sınırı

Güvenli Uygulama Başlatma — Symlink Bypass Koruması

Güçlü

launch_application() fonksiyonu kanonik yol kontrolü yaparak sembolik linklerin kara listeyi atlatmasını önlüyor. Yalnızca /usr/bin/, /bin/, /usr/local/bin/, /usr/games/ ve /opt/ altındaki programlar çalıştırılabiliyor.

AI Ajan Güvenliği — Onay Zinciri ve Eylem Kısıtlama

Güçlü
  • AI'ın yürütebileceği komutlar ALLOWED_AGENT_ACTIONS ile kısıtlı (8 komut)
  • Her AI eylemi kullanıcı onayı gerektiriyor (Confirm Modal)
  • Ollama uç noktası yalnızca 127.0.0.1 / localhost ile kısıtlı
  • SSRF koruması: 169.254.169.254 (bulut metadata) ve metadata.google.internal engelli
  • Custom endpoint'ler HTTPS veya localhost olmak zorunda
  • HTTP redirect takibi kapatılmış (Policy::none()) — redirect-based SSRF engelli

XSS Koruması — escapeHtml() Tutarlı Kullanımı

Güçlü

Frontend tarafında tüm kullanıcı verisi (paket adları, dosya adları, disk bilgileri) escapeHtml() fonksiyonu ile HTML-encode edilerek DOM'a yazılıyor. &, <, >, ", ' karakterleri kaçırılıyor. AI yanıtları textContent ile render ediliyor, innerHTML kullanılmıyor.

Güvenli Kurulum Motoru — Input Validation ve STDIN Pipe

Güçlü
  • Disk hedefi regex doğrulaması: Sadece /dev/sd[a-z]+, /dev/vd[a-z]+, /dev/nvme<N>n<N> kabul ediliyor
  • Bölüm (partition) seçimi engelli — yalnızca tam disk seçilebilir
  • Kullanıcı adı/hostname RFC uyumlu doğrulama
  • Parola chpasswd'ye STDIN pipe ile iletiliyor — komut satırı argümanında görünmüyor
  • Null byte ve newline enjeksiyonu engelleniyor

Derlemede Güvenlik Optimizasyonları

Güçlü
  • opt-level = "s" → ikili boyut optimizasyonu
  • lto = true → bağlayıcı optimizasyonu (dead code elimination)
  • panic = "abort" → unwinding yerine abort (stack bilgi sızıntısı azaltma)
  • strip = true → hata ayıklama sembollerinin kaldırılması
  • codegen-units = 1 → tekil derleme birimi (daha iyi optimizasyon)

📊 Sonuç ve Genel Değerlendirme

Ankora Linux Ayaz DE v2.0.0 kod tabanı, bir kiosk masaüstü ortamı için ortalamanın üzerinde güvenlik önlemleri barındırmaktadır. Özellikle komut yürütme motoru, dosya erişim katmanı ve AI ajan güvenlik zinciri endüstri standartlarına uygun tasarlanmış ve katmanlı savunma (defense-in-depth) ilkesi doğru uygulanmıştır.

Kritik seviyede güvenlik açığı tespit edilmemiştir. Raporda belirtilen 2 yüksek ve 5 orta seviye bulgu, yukarıdaki aksiyon planı izlenerek kapatılabilir. Tüm öneriler uygulandığında güvenlik puanının 90+ seviyesine ulaşması beklenmektedir.

Projenin en güçlü yanları: minimal Tauri API yüzeyi, XSS korumasında tutarlılık, SSRF önlemlerinin kapsamlılığı ve derleme zamanı güvenlik optimizasyonlarıdır.
